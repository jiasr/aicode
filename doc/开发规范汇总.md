## 一、数据库与后端规范

### 1. 新表主键统一使用 UUID
mallservice-python 项目中**新建**数据库表时，主键 id 一律使用 UUID（`VARCHAR(32)`，`uuid4().hex` 格式），不使用 `INT AUTO_INCREMENT`。该规范只适用于往后新建的表，已有表（INT 自增主键）不做迁移改造。`t_mall_printer_config` 是首个遵循该规范的表。（来源：Qoder）

### 2. Flask-RestX 路由注册必须同时执行 Blueprint 与 Namespace
在 `mall/__init__.py` 中注册新的 Flask-RestX 路由模块时，必须同时执行两步：
1. `app.register_blueprint(app_xxx, url_prefix="/...")` —— Flask 层面的 Blueprint 注册
2. `api.add_namespace(ns_xxx)` —— Flask-RestX 层面的 Namespace 挂载

仅注册 Blueprint 不会自动将路由挂载到 API 实例上，漏掉 `add_namespace` 会导致新路由 404。所有新增的 `router_*.py` 文件均需遵循。（来源：Qoder）

### 3. 打印流水触发方式枚举（trigger_type）
`t_mall_print_log` 表的 `trigger_type` 字段（`VARCHAR(16)`）标识小票打印触发来源：
- `auto`：支付成功回调后自动触发打印
- `manual`：用户在前端订单列表点击「补打小票」按钮手动触发
- `test`：管理员在配置页进行「测试打印」时触发

服务层调用 `print_ticket()` 时需显式传入对应值；查询接口 `list_logs()` 需返回该字段供前端展示。（来源：Qoder）

### 4. 回调日志使用中文并详细记录
回调处理的日志需使用中文记录，并包含完整链路信息：收到回调（含来源 IP）、参数解析、验签结果、流水匹配、状态变更及重复推送识别，便于问题排查。（来源：Qoder）

## 二、飞鹅打印规范

### 1. 打印内容使用全角人民币符号 ￥
生成打印小票内容时，货币符号必须使用**全角 `￥`（U+FFE5）**，禁止使用半角 `¥`（U+00A5）。飞鹅打印机使用 GB2312/GBK 字库，不包含半角 ¥ 码位，转码后会显示为乱码（如「01」）。（来源：Qoder）

### 2. 飞鹅 `<L>` 标签非左对齐而是字体变高一倍
飞鹅打印机指令中 `<L>` 标签的实际效果是**字体变高一倍**，并非普通左对齐；`<C>` 才是正常字号居中。需要正常字号时避免使用 `<L>` 标签，普通行不加标签即为正常字号左对齐。（来源：Qoder）

### 3. 回调自动打印启用条件判断
支付回调处理小票打印时，必须先检查飞鹅配置的启用开关（`enabled=1`）、设备是否存在；若未启用或无设备，则跳过打印但正常完成订单更新，仅记录日志提示，不影响支付流程。（来源：Qoder）

### 4. 飞鹅打印设备策略配置
支持两种设备策略，配置存储于品牌配置的 `config_json` 中，前端提供切换选项：
- **默认设备**：固定使用配置中指定的打印机（通过 `defaultSn` 指定）
- **轮询**：在所有已启用设备中轮流分配打印任务，计数器取模选择，单台失败不阻塞后续轮转（来源：Qoder）

### 5. 小票条码仅展示纯文本
小票打印中商品条码仅以纯文本形式展示，不使用图形化条码（如 SVG），直接显示条码数字字段，确保只要接口返回即可稳定呈现。（来源：Qoder）

### 6. 已打印订单的二次打印确认流程
订单已有打印记录时，点击「补打小票」需先查后台最新打印记录，已提交（status=0）/打印成功（status=1）时弹出包含**完整打印记录**的对话框（触发方式、设备 SN、状态、飞鹅订单 ID、打印时间、备注），用户必须手动点击「继续打印」才提交打印任务；默认焦点在「取消」按钮，支持 Esc 关闭。查询失败不阻断打印。（来源：Qoder）

### 7. 小票机配置页布局与提示文案规范
配置页布局顺序：
1. **启用开关**：独立一行置顶显示
2. **账号配置**：开发者账号/密钥输入框 + 保存按钮紧随下方
3. **打印策略**：默认设备选择与轮询模式单选
4. **打印机列表**：设备 SN/KEY/备注/在线状态表格
5. **打印结果回调**：位于打印机列表下方、测试打印上方，独立成区（含回调地址、验证 Token、验证地址、两步配合说明）
6. **测试打印**：独立区域放在最底部

提示文案规范：回调地址输入框下方常驻显示完整地址模板（不依赖 placeholder，支持手动选中复制）；验证地址自动生成后纯文字展示；避免使用「复制按钮」作为主要交互方式。（来源：Qoder）

## 三、前端样式与交互规范

### 1. 57mm 热敏小票样式规范
| 项目 | 规格 |
|---|---|
| 有效打印宽度 | 48mm（≈181px @96dpi） |
| 字体 | Courier New 等宽，基础字号 9px |
| 条码字号 | **8px**（13 位数字 + 分隔符控制在 67px 内，防止折行） |
| 分隔线 | 24 个 `-` 字符 |
| 商品明细布局 | 左侧：`条码 | 名称 (规格)`（紧凑单行，条码 8px 加粗）；右侧：`单价 x 数量 小计`（固定 106px，与表头对齐） |
| 超长处理 | 名称过长时在左侧换行，右侧价格列永不折行 |
| 条码展示 | 纯文本形式，无条码时隐藏该行 |
（来源：Qoder）

### 2. 80mm 订单小票前端样式规范
订单小票打印页面采用 80mm 热敏纸样式：等宽字体，内容宽度控制在 72mm 内，实付金额加粗突出显示。（来源：Qoder）

### 3. 窄票打印中条码折行的像素级测算与修复方法
窄屏布局中遇到元素折行时，先进行像素级测算：
1. 容器总宽 - 固定区域宽 = 可用宽
2. 字体字符宽 = 字号 × 字宽系数（等宽字体 ≈ 0.6）
3. 内容字符数 × 字符宽 ≤ 可用宽，否则缩小字号或压缩间距

案例：57mm 小票（181px）右侧价格区固定 106px，左侧剩 73px；13 位条码 + 分隔符 14 字符 × 5.4px（9px 字号）= 75.6px 超宽折行 → 字号降为 8px（14 × 4.8px = 67.2px）+ `white-space: nowrap` 解决。（来源：Qoder）

### 4. el-table 操作列占用剩余空间
需要某一列占用表格剩余空间时，将该列设置为 `min-width` 并移除 `fixed` 属性，使其参与剩余空间分配（如「操作」列大屏下动态扩展）。其余列用固定 `width`，避免 `min-width` 列被意外拉伸。（来源：Qoder）

### 5. 订单列表左右布局与状态平铺规范
订单列表采用**左搜索栏右表格**两栏布局：
- 左侧固定宽度面板（200px），自上而下：订单状态平铺（全部/待付款/待发货/已发货/已签收/已完成/已取消，当前状态蓝色高亮）+ 搜索表单（订单号/收货人/手机号竖向排列 + 搜索/重置按钮全宽）
- 右侧 el-card 占满剩余空间，含表格与分页
- 点击状态 → 重置到第 1 页 → 按状态加载；搜索关键词与状态可叠加过滤
- 左侧面板需 `overflow-y: auto`，状态项间距 10px、padding 8-12px（来源：Qoder）

### 6. 订单列表商品信息折叠展示规则
商品信息列最多展示 2 件商品的详细信息（含图片、名称、规格、数量），超出部分显示「等 N 件商品」提示，避免表格行过高。（注：当前线上实现为全量展示 + 窄列 180px，折叠方案曾回退，两种模式按需取舍）（来源：Qoder）

### 7. 小票按钮命名与位置规范
- **首次打印**：「打小票」；**二次打印**：「补打小票」（Printer 图标）
- **预览**：「小票预览」（Tickets 图标，打开打印预览页新窗口）
- 位置：补打小票、小票预览按钮放在**小票状态列下方**竖排（列宽 110px），与状态标签绑定；操作列只保留业务按钮（查看/发货/取消/退款/删除），`min-width` 弹性占满剩余空间
- link 按钮需清除默认 margin-left（`:deep(.el-button)` 处理）（来源：Qoder）

### 8. 后台敏感输入框防自动填充与密码切换实现规范
- 阻止自动填充：文本输入框设 `autocomplete="off"`；密码输入框必须用 `autocomplete="new-password"`（Chrome 对 password 类型用 off 无效）
- 密码可见性切换：Element Plus 的 `show-password` 在动态 `:type` 绑定下可能失效，改用 `#suffix` 插槽放图标手动切换 `type`（password/text），用 `reactive` 对象管理各字段可见性状态（来源：Qoder）

### 9. 前端表单动态渲染机制
前端表单根据后端返回的品牌字段 schema 动态渲染：品牌接口提供 `configFields` 和 `deviceFields` 定义，前端依据 `type`、`label`、`required` 等属性生成对应输入控件，新增品牌无需修改前端代码。（来源：Qoder）

### 10. 时间轴动态节点渲染约定
前端时间轴组件应根据后端返回的状态和时间数据动态渲染节点，仅展示已发生的事件节点；未完成或不存在的数据节点自动隐藏，避免显示空值或占位符。（来源：Qoder）

## 四、业务规则

### 1. 订单号去除 CH 前缀
- 新订单号生成格式：`{年月日时分秒毫秒}{6位随机数}`（无 CH 前缀，毫秒时间戳 + 随机数保证全局唯一，不依赖数据库流水号）
- 历史订单（CH 开头）原样展示，不做数据清洗
- 全链路（搜索、回调、小票打印）均不依赖该前缀，订单号采用模糊匹配（来源：Qoder）

### 2. 无自动取消机制的运行现状
系统目前**没有**「未支付自动取消」定时任务（`mall/cmd/task.py` 为空文件）；微信支付侧有 2 小时支付时效（超时后用户无法再支付），但订单状态会停留在「待付款」，不会自动变为「已取消」。如需自动取消需另行实现定时任务。（来源：Qoder）

## 五、源码管理约定

### 1. aicode 父仓库子模块指针更新提交约定
- `e:\aicode` 是 git 父仓库（superproject），mall-admin、mallservice-python、mall-littleprogram、SDK_ReleaseforAndroid、jinxiaocun 为其子模块
- 子仓库代码提交推送后，需在父仓库同步 `git add` 对应子模块路径并提交推送指针更新（提交信息惯例：`chore: 更新子模块指针(简要说明)`），否则父仓库源码管理面板会持续显示子模块 M 变更
- 父仓库推送前先 `git pull --rebase` 合并远程提交
- `mall/common/gds_token.json` 为运行时登录 token 缓存，不参与提交（每次登录自动刷新）（来源：Qoder）

### 2. git 协作纪律（提交铁律）
多工具、多人协作下防止 git 混乱的强制性规则，任何人提交前必须遵守：（来源：CodeBuddy）
- **铁律 1：push 前必须先拉**。任何仓库 push 之前先 `git pull --rebase`，禁止直接 push 产生分叉；若已有分叉必须 rebase 合并
- **铁律 2：原子提交**。一个 commit 只做一件事（如"修复支付回调 bug"与"新增运费设置页"必须分开提交），禁止混提
- **铁律 3：子模块联动**。子仓库提交推送后，必须立即在父仓库更新子模块指针并提交推送（见五.1），禁止只推子仓库不同步父仓库
- **铁律 4：禁止敏感信息入库**。运行时缓存、token、密钥（如 `mall/common/gds_token.json`）一律不提交，进 `.gitignore`
- **铁律 5：文档修改走正规流程**。改 `doc/*.md` 需同时：更新顶部「更新日期」、按「标注身份」注明来源、说明修改原因，随代码一起提交或单独提交
- **铁律 6：提交信息规范**。格式 `<type>: <中文描述>`，type 限 `feat` / `fix` / `chore` / `docs` / `refactor` / `style` / `test`；描述控制在 50 字内，说明"改了什么、为什么"，不写空话（如"update"、"修改"）

### 3. 提交前检查清单（check-commit.ps1）
提交前在 `e:\aicode` 根目录运行 `check-commit.ps1`（Windows PowerShell）自动检查，逐项自查如下：（来源：CodeBuddy）
1. 工作区是否干净（无未提交改动、无新文件漏 add）
2. 所有子模块是否有未提交/未推送的提交
3. 当前分支与远程是否同步（无 ahead/behind 分叉）
4. 提交信息是否符合 `<type>: <中文描述>` 规范
5. 是否误带敏感文件（token、密钥、日志、本地配置）
6. 是否同步了父仓库子模块指针（若有子仓库提交）
全部 PASS 再 push；任一 FAIL 先修复。

**运行方式**：
```powershell
cd e:\aicode
powershell -ExecutionPolicy Bypass -File .\check-commit.ps1
```

**检查内容与输出**：脚本输出一张 PASS/FAIL 表格，覆盖 4 类检查 —— ① 父仓库工作区未提交改动；② 每个子模块的脏工作区/未推送提交/落后远程/分叉状态；③ 父仓库子模块指针是否与子模块一致；④ 敏感文件（`gds_token`、`.env`、`*.key`、`*.pem`、`password`、`secret`）是否被 git 跟踪。退出码 0=全部通过，1=存在 FAIL。

**说明与注意事项**：
- 脚本本身做**提示检查**；同时已配置 **git pre-push hook 强制拦截**（见下），两者配合实现"先检查、后推送"
- 脚本输出为纯 ASCII（避免 Windows PowerShell 5.1 对 UTF-8 中文的解析问题）
- 运行需系统已安装 git，且当前目录为 aicode 父仓库根目录（否则脚本提示 location FAIL）
- 脚本文件本身随父仓库提交维护（提交信息惯例：`chore: 更新提交检查脚本`）

### 4. pre-push hook 自动检查（git 层强制）
父仓库已启用 git hook：**任何方式（AI 命令行、人工、IDE）执行 `git push`，都会自动先运行 `check-commit.ps1`，检查 FAIL 则中断推送**，从机制上杜绝乱提交。（来源：CodeBuddy）
- **实现**：`git config core.hooksPath .githooks`，hook 脚本为 `.githooks/pre-push`
- **生效范围**：只对**已执行该配置的本地仓库**生效；新克隆的仓库需重新执行一次 `git config core.hooksPath .githooks`（hook 路径配置存于 `.git/config`，不随仓库提交，但 `.githooks/pre-push` 文件本身随仓库提交）
- **强制跳过**：仅限确实需要时 `git push --no-verify`，跳过前务必确认改动合规
- **注意**：hook 依赖 Windows + Git Bash 环境（调用 powershell.exe）；`.githooks/` 目录随父仓库提交维护
